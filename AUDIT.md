# Аудит Clipboard Exchange — 2026-09-06

Исходный аудит охватывал рабочее дерево, включая незакоммиченные изменения и каталог desktop. Описания проблем и номера строк ниже относятся к состоянию до исправлений. Результаты последующей реализации приведены в следующем разделе.

## Исправления

Все девять пунктов реализованы в рабочем дереве:

| № | Изменение | Регрессионная проверка |
|---|---|---|
| 1 | Проверка метода, статуса, объёма, ошибок записи и flush; preview не расходует файл | HEAD/304/412/Range/inline, сбои файла и ZIP, браузерное скачивание |
| 2 | Общий lifecycle lock охватывает HTTP-операции и весь проход cleanup со снимком ссылок; занятый проход повторяется через 5 с | Maintenance не проходит через активную публикацию и не блокирует новые запросы в ожидании загрузки |
| 3 | Сериализация операций upload; результат complete сохраняется в SQLite; ошибка не удаляет объект | 8 параллельных complete, неверная capability, новый handler, проверка содержимого |
| 4 | Дедлайны обновляются по мере чтения/записи потока | Реальный HTTP-сервер с истёкшим абсолютным тайм-аутом |
| 5 | Целая UTF-16 строка преобразуется в UTF-8 до JSON-экранирования | Native Unicode codec и открытый/зашифрованный HTTP round trip |
| 6 | Расшифровка и ZIP используют pull с нулевой очередью и AbortController | Backpressure, cancel, повреждённый ciphertext, ZIP CRC и полное получение |
| 7 | Принимается только последний валидный IP в XFF; Forwarded игнорируется; пример nginx перезаписывает заголовок | Подставленные prefix/Forwarded не меняют IP |
| 8 | `/history?limit=0..30` с бюджетом 8 МиБ; desktop отправляет текст после запроса только metadata | Native round trip в комнате >16 МиБ; серверная проверка большой комнаты |
| 9 | Readiness проверяет БД и запись в хранилище; deadline 2 с, cache 1 с, одна проверка одновременно | Удаление/восстановление каталога, закрытая БД, независимый healthz |

Уточнение исходного аудита: API и Web UI уже запрещали download-once для нескольких
вложений или сообщения с текстом. Поэтому сценарий удаления остальных вложений не
был достижим через штатное создание сообщения. Реальным воспроизведённым дефектом
были HEAD и отсутствие проверки результата передачи. Ограничение одного файла
сохранено; обработчики удаления дополнительно проверяют его.

Обновление автоматически создаёт схему SQLite 7. Для отката нужен backup старой
схемы; новый Windows-клиент требует обновлённый сервер с `/history`. Download-once
подтверждает передачу браузеру, а не запись на диск; параллельные читатели не
исключаются. Отдельный CLI reconcile необходимо запускать при остановленном сервере.

Проверки после исправлений: штатные и новые Go-тесты; 17 Node-тестов; 7 CTest-тестов;
native HTTP round trip в открытой, encrypted и большой комнате; Chrome E2E —
17 успешных сценариев и один штатный skip; мобильный профиль — 4/4. Локальный race detector не собрался из-за устаревшего MinGW
(отсутствуют WaitOnAddress/WakeByAddress*); Linux race job в CI сохранён. Firefox
не смог создать страницу: Playwright завершает `browserContext.newPage` с ошибкой
`Cannot read properties of undefined (reading '_page')` ещё до выполнения шагов
приложения. Эти две проверки нельзя считать пройденными.

P1 — исправить до следующего стабильного релиза: потеря данных или нарушение основного сценария. P2 — следующий этап: корректность, устойчивость и эксплуатационная безопасность. Порядок ниже — рекомендуемая очередь работ. Для гонок приведено допустимое чередование операций, но стресс-воспроизведение не проводилось.

## 1. P1: «Скачать один раз» удаляет данные без успешного скачивания

**Код:** `internal/httpserver/server.go:814–827`, `:958–975`.

После `http.ServeContent` проверяется только отсутствие заголовка Range. Не проверяются метод, статус ответа и успешность передачи. HEAD попадает в GET-маршрут и удаляет запись без тела ответа. Аналогично опасны условные запросы и оборванное скачивание. Удаляется вся entry; штатный API ограничивает download-once одним файлом без текста.

**Подтверждение:** временный тест на основе штатного `TestDownloadOnceDeletesOnlyAfterFullResponse`: создать одноразовый файл, выполнить HEAD, затем GET. HEAD вернул 200, GET — 404 `not_found`. Тест удалён после проверки.

**Доработка:** определить явную семантику одноразового сообщения и подтверждения получения; HEAD/304/ошибки передачи не должны потреблять запись. Для нескольких файлов удалять сообщение после получения всей группы или использовать отдельное подтверждение. Добавить проверки HEAD, 304, обрыва, Range, отдельных вложений и архива.

## 2. P1: фоновая очистка конфликтует с текущими загрузками

**Код:** `cmd/clipboard-exchange/main.go:145–150`; `internal/filestore/filestore.go:185–205`; `internal/store/store.go:1202`.

Reconcile запускается при старте и каждый час одновременно с HTTP. Он получает снимок ссылок, затем удаляет всё, чего в снимке нет. Между этими действиями может создаться новая upload-сессия, и её каталог будет удалён. Также сборка создаёт `.object-*` непосредственно в дереве objects, а Reconcile считает такой временный файл бесхозным. На Linux unlink открытого временного файла приведёт к сбою последующей публикации через hard link; на Windows возможна ошибка удаления открытого файла.

**Доработка:** синхронизировать очистку с жизненным циклом файлов; выделить временную область и защищать активные операции. Исключение только `.object-*` недостаточно: остаётся устаревший снимок новых upload ID. Проверка: управляемое пересечение создания/сборки файла с Reconcile не должно терять данные.

## 3. P1: параллельный complete может удалить успешно опубликованный файл

**Код:** `internal/httpserver/server.go:744–757`; `internal/filestore/filestore.go:133–148`; `internal/store/store.go:926–970`.

Два запроса complete одной сессии могут пройти авторизацию и сборку. Assemble допускает уже существующий объект с тем же digest. Первый запрос фиксирует запись files и удаляет uploads; второй получает ошибку из CompleteUpload и безусловно вызывает RemoveObject. В итоге БД содержит файл, а объекта на диске нет. Сценарий возможен при конкурентных повторах одного запроса.

**Доработка:** сделать завершение идемпотентным и сериализовать переход состояния сессии; ошибочный повтор не должен удалять объект, принадлежащий завершённой операции. Проверка: два синхронных complete, затем успешное чтение файла и согласованная БД.

## 4. P1: общий тайм-аут 30 секунд обрывает большие скачивания

**Код:** `cmd/clipboard-exchange/main.go:76–77`; `internal/httpserver/server.go:780`, `:830`.

Обработчики файла и ZIP не переопределяют общий WriteTimeout. Передача 500 МиБ за 30 секунд требует примерно 16,7 МиБ/с полезной скорости; более медленные соединения не укладываются. Тайм-аут абсолютный, а не тайм-аут отсутствия прогресса. В сочетании с пунктом 1 обрыв может уничтожить одноразовую запись. ReadTimeout также ограничивает длительность загрузки каждого чанка.

**Доработка:** настроить отдельную политику дедлайнов для потоковых маршрутов, сохранив защиту от зависших соединений. Проверять через настоящий HTTP-сервер с production-тайм-аутами и ограничением скорости: httptest.NewServer из текущих тестов эти настройки не применяет.

## 5. P2: Windows-клиент повреждает emoji и другие символы вне BMP

**Код:** `desktop/windows/src/room_client.cpp:360–372`.

JsonEscape перебирает отдельные wchar_t и каждый отдельно конвертирует в UTF-8. В Windows символы вне BMP представлены парой UTF-16 surrogate; конвертация половинок по отдельности не сохраняет исходный символ. Это затрагивает как открытый текст, так и payload перед шифрованием.

**Доработка:** конвертировать целую строку в UTF-8 перед JSON-экранированием либо использовать корректный JSON-сериализатор. Критерий: побайтовый round trip текста с кириллицей, emoji, музыкальными символами и переносами строк через открытые и зашифрованные комнаты. Вывод статический; Win32-тест не запускался.

## 6. P2: потоковая расшифровка не учитывает скорость потребителя

**Код:** `internal/httpserver/web/download-sw.js:67–91`, `:95–134`.

Оба ReadableStream читают и расшифровывают все чанки из async start и безусловно вызывают enqueue. Нет pull, проверки backpressure или cancel/AbortController. Поэтому при медленном потребителе очередь может накопить значительную часть файла/архива — потребление памяти не ограничено размером чанка. Завершение цикла и вызов consume также не означают, что пользователь сохранил данные.

**Доработка:** выдавать ограниченное число чанков по pull, прерывать сетевые запросы при cancel; увязать consume с выбранной в пункте 1 семантикой. Проверка: медленный читатель и отмена большого encrypted-download, ограниченная память и прекращение сетевых запросов. Измерение памяти в браузере не проводилось.

## 7. P2: rate limit обходится через подставленные proxy-заголовки

**Код:** `internal/httpserver/server.go:1131–1144`; пример nginx в README.md.

При TrustProxy берётся произвольное значение Forwarded, а при его отсутствии — самый левый X-Forwarded-For. В рекомендованном nginx-примере `$proxy_add_x_forwarded_for` сохраняет присланную клиентом цепочку; Forwarded отдельно не перезаписывается. Клиент может менять эти значения и получать новый лимит даже при полностью закрытом прямом доступе к Go-серверу. Это затрагивает и лимит получения short-link envelope.

**Доработка:** определить доверенные proxy и разбирать цепочку справа налево либо документировать и применять перезапись обоих заголовков на входном proxy. Проверка: различные подставленные Forwarded/XFF от одного клиента за proxy используют один счётчик. Вывод по коду и конфигурации; настоящий nginx не запускался.

## 8. P2: Windows-клиент перестаёт работать с допустимой большой комнатой

**Код:** `desktop/windows/src/room_client.cpp:188–198`, `:396–407`; `internal/httpserver/server.go:366`; лимиты config.

Клиент ограничивает ответ 16 МиБ, но сервер разрешает 500 записей по 65536 байт — уже около 31,25 МиБ текста без JSON и base64. FetchRoom загружает весь snapshot; SendRoomText также сначала вызывает FetchRoom. Поэтому законно заполненная комната блокирует не только историю, но и отправку из desktop.

**Доработка:** добавить API ограниченной/постраничной истории, отдельно получать метаданные комнаты перед отправкой. Простое увеличение лимита оставит лишнюю передачу всей истории при каждом обновлении. Проверка: комната с максимально разрешённым объёмом текста остаётся доступной для просмотра последних сообщений и отправки.

## 9. P2: readiness всегда сообщает об исправности

**Код:** `internal/httpserver/server.go:84`.

`/readyz` безусловно возвращает 204, как `/healthz`. При недоступной БД или файловом хранилище балансировщик и эксплуатационные проверки продолжат считать экземпляр готовым. README предлагает этот endpoint как проверку после restore.

**Доработка:** отделить liveness от readiness; выполнять ограниченные по времени проверки БД и доступности хранилища. Критерий: отказ зависимости даёт 503, восстановление — успешный статус; проверка не создаёт существенную нагрузку.
